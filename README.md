# 🧩 Nest Template

Шаблон API на NestJS с PostgreSQL, Prisma, проверкой переменных окружения, Swagger и единым форматом ответов.

## Что входит в шаблон

- **Основа:** NestJS и TypeScript.
- **База данных:** PostgreSQL, Prisma Client и адаптер `@prisma/adapter-pg`.
- **Docker:** Dockerfile для сборки API на Node.js 26 и Docker Compose для запуска PostgreSQL 17, применения миграций и запуска API.
- **HTTP API:** версионирование через URL, настроенный `ValidationPipe`, CORS, Swagger, общий фильтр ошибок и перехватчик ответов.
- **Ограничение запросов:** глобальный `ThrottlerGuard` — до 100 запросов за 60 секунд с одного IP на каждый маршрут.
- **Конфигурация:** `@nestjs/config` и проверка переменных окружения через Joi.
- **Авторизация:** JWT-модуль, `AuthGuard`, декораторы `@Auth()` и `@CurrentUser()`.
- **Стиль кода:** ESLint, Prettier, Husky и `lint-staged`.

## 🚀 Быстрый старт

Для локальной разработки нужны Node.js 26.x и npm 11.x согласно `package.json`. Dockerfile и CI также используют Node.js 26. В этом варианте NestJS работает локально с перезапуском при изменении кода, а PostgreSQL — в Docker. Для базы нужны Docker и Docker Compose; вариант без Docker описан ниже.

```bash
cp .env.example .env
npm ci
docker compose up -d --wait postgres
```

При установке зависимостей `postinstall` автоматически генерирует Prisma Client. Проверьте значения в `.env`: пользователь, пароль и название базы в `DATABASE_URL` должны совпадать с `DATABASE_USER`, `DATABASE_PASSWORD` и `DATABASE_NAME`. Для локального API адрес базы — `localhost:5432`. Остальные переменные описаны ниже.

Если в проекте есть миграции, примените их к базе:

```bash
npm run prisma:migrate:deploy
```

Запустите приложение:

```bash
npm run start:dev
```

По умолчанию приложение слушает `http://localhost:3001`. Доступность API можно проверить по адресу `http://localhost:3001/health`, а Swagger открыть по адресу `http://localhost:3001/docs`.

### Запуск без Docker

Установите PostgreSQL отдельно, создайте пользователя и базу. Скопируйте `.env.example` в `.env` и укажите подключение к этой базе в `DATABASE_URL`.

```bash
npm ci
# Если в проекте есть миграции
npm run prisma:migrate:deploy
npm run start:dev
```

В этом режиме команды Docker не нужны. Приложение использует `DATABASE_URL`; переменные `DATABASE_USER`, `DATABASE_PASSWORD` и `DATABASE_NAME` нужны для настройки сервисов Compose.

## Запуск через Docker

Для запуска API и PostgreSQL в контейнерах нужны Docker и Docker Compose. Если `.env` ещё не создан, скопируйте `.env.example` в `.env` и настройте значения.

```bash
docker compose up -d --build
```

Compose собирает образы по `Dockerfile` и запускает сервисы в следующем порядке:

1. `postgres` запускается и проходит `healthcheck`.
2. `migrate` выполняет `npm run prisma:migrate:deploy` и завершается.
3. `api` запускается после успешного завершения `migrate`. Ошибка миграций блокирует запуск нового контейнера API.

API доступен на `http://localhost:3001`, Swagger — на `http://localhost:3001/docs`. Локальный API на этом же порту перед запуском контейнера нужно остановить.

В контейнер API передаются переменные из `.env`, но `DATABASE_URL` переопределяется в Compose: адрес базы внутри сети контейнеров — `postgres:5432`. В самом `.env` оставьте `localhost:5432` для локальной разработки. Публикация порта API использует `${PORT:-3001}`: при изменении `PORT` в `.env` меняются и порт приложения, и опубликованный порт хоста. Адреса выше приведены для значения по умолчанию `3001`.

Порт PostgreSQL опубликован только на `127.0.0.1:5432`, а порт API — на всех сетевых интерфейсах хоста. Для доступа к API только с этого компьютера укажите в `ports` сервиса `api` значение `127.0.0.1:${PORT:-3001}:${PORT:-3001}`.

Dockerfile отдельно собирает NestJS и генерирует Prisma Client, затем переносит `dist` в финальный образ с production-зависимостями. Приложение запускается от пользователя `node`. `.dockerignore` исключает из контекста сборки локальные зависимости, готовую сборку и `.env`.

```bash
# Состояние сервисов, включая завершившийся migrate
docker compose ps -a

# Результат применения миграций
docker compose logs migrate

# Логи API
docker compose logs -f api

# Остановка контейнеров с сохранением базы
docker compose down
```

Данные PostgreSQL сохраняются в томе `postgres_data`. Команда `docker compose down -v` удаляет этот том вместе с данными базы. Переменные `POSTGRES_*` настраивают базу при первой инициализации пустого тома: изменение `.env` не меняет существующих пользователей и пароли.

После изменения кода повторите `docker compose up -d --build`: автоматический перезапуск при редактировании исходников в контейнере не настроен. Для локальной разработки используйте запуск только базы из раздела «Быстрый старт» и `npm run start:dev`. Если контейнер API уже работает, сначала остановите его командой `docker compose stop api`.

Сервис `migrate` использует этап `build` из Dockerfile, где установлен Prisma CLI и скопирована схема вместе с файлами миграций, если они созданы. Финальный образ API не содержит Prisma CLI. Статус `Exited (0)` у `migrate` означает успешное завершение, а не сбой.

## Миграции базы данных

В исходном шаблоне пока нет моделей и папки `prisma/migrations`. После добавления моделей в `prisma/schema.prisma` создайте миграцию локально, подключившись к базе разработки:

```bash
npm run prisma:migrate -- --name create_users
npm run prisma:generate
```

Замените `create_users` на имя вашего изменения. Сохраните схему и созданные файлы в `prisma/migrations` в Git. `prisma:generate` обновляет Prisma Client, но сама по себе эта команда не создаёт таблицы.

Для применения готовых миграций при локальном запуске используйте `npm run prisma:migrate:deploy`. При запуске всего проекта через `docker compose up -d --build` эту команду выполняет сервис `migrate`. Она применяет ещё не применённые миграции, но не создаёт новые. `db push` автоматически не выполняется.

## Переменные окружения

Пример значений находится в `.env.example`. При запуске приложение проверяет обязательные переменные и завершает работу с ошибкой, если они некорректны.

| Переменная              | Назначение                                                        |
| ----------------------- | ----------------------------------------------------------------- |
| `PORT`                  | Порт API; по умолчанию `3001`                                     |
| `DATABASE_URL`          | Строка подключения к PostgreSQL                                   |
| `DATABASE_USER`         | Пользователь PostgreSQL, создаваемый через Compose                |
| `DATABASE_PASSWORD`     | Пароль пользователя PostgreSQL для Compose                        |
| `DATABASE_NAME`         | Название базы, создаваемой через Compose                          |
| `FRONTEND_URL`          | Разрешённый адрес фронтенда для CORS                              |
| `JWT_ACCESS_SECRET`     | Секрет подписи access-токенов, минимум 16 символов                |
| `JWT_ACCESS_EXPIRES_IN` | Срок действия access-токена в секундах, положительное целое число |

Значения секретов и паролей в `.env.example` приведены для примера. Перед развёртыванием задайте собственные значения; для `JWT_ACCESS_SECRET` используйте случайно сгенерированный секрет.

## Версионирование API

В `src/main.ts` включено версионирование через URL (`VersioningType.URI`). Маршруты без явно заданной версии получают префикс `/v1` благодаря `defaultVersion: '1'`. Например, контроллер с путём `users` и методом `@Get()` будет доступен по адресу `GET /v1/users`.

- Версию контроллера можно задать через `@Controller({ path: 'users', version: '2' })`, а версию отдельного метода — через `@Version('2')`. Поэтому в одном приложении могут сосуществовать, например, `/v3/users` и `/v1/auth`.
- Новую версию маршрута имеет смысл вводить при несовместимом изменении контракта. Пока старые клиенты используют прежний контракт, сохраняйте для них обработчик предыдущей версии. Если обе версии должны вести себя одинаково, можно назначить их одному обработчику через `@Version(['1', '2'])`.
- Встроенный `GET /health` помечен `@Version(VERSION_NEUTRAL)` и доступен без префикса версии. Он проверяет доступность API без обращения к базе данных.

Вызов `app.enableVersioning()` находится перед генерацией документа Swagger и запуском сервера. Интерфейс Swagger открывается по адресу `/docs`. Значение `setVersion('1.0')` в настройках Swagger задаёт версию в метаданных OpenAPI. Префикс маршрутов задаётся настройками NestJS.

## Ограничение частоты запросов

В `src/app.module.ts` подключены `ThrottlerModule` и глобальный `ThrottlerGuard`. Для каждого IP разрешено до 100 запросов за 60 секунд на каждый маршрут отдельно. При превышении лимита API возвращает HTTP `429 Too Many Requests`. Ограничение действует и на публичные маршруты, включая `GET /health`.

Лимит задаётся в `ThrottlerModule.forRoot()`: `ttl: 60_000` — интервал в миллисекундах, `limit: 100` — число запросов. Сейчас значения заданы в коде и не настраиваются через `.env`. Для отдельных маршрутов можно переопределить настройки декоратором `@Throttle()` или отключить ограничение через `@SkipThrottle()` из `@nestjs/throttler`.

Счётчики хранятся в памяти процесса и сбрасываются при перезапуске. При запуске нескольких экземпляров API у каждого будут собственные счётчики; для общего лимита нужно подключить общее хранилище. При размещении за reverse proxy настройте доверенные прокси в HTTP-адаптере, чтобы ограничение учитывало IP клиента.

## Авторизация

`JwtAuthModule` подключён глобально и предоставляет `JwtService` с секретом и сроком действия из переменных окружения. В шаблоне подготовлена проверка access-токенов; вход, регистрация, выдача и обновление токенов, выход и проверка пользователя в базе пока не реализованы.

Для защиты маршрута или всего контроллера добавьте `@Auth()`. Guard ожидает заголовок `Authorization: Bearer <access_token>`, проверяет подпись JWT, срок действия при наличии `exp` и непустой строковый `sub`. После проверки в `request.user` записывается `{ sub }`, доступный через `@CurrentUser()`.

```ts
import { Controller, Get } from '@nestjs/common';

import { Auth } from '@/common/decorators/auth.decorator';
import { CurrentUser } from '@/common/decorators/current-user.decorator';
import type { AuthUser } from '@/common/types/auth-user.types';

@Controller('profile')
export class ProfileController {
  @Get()
  @Auth()
  getProfile(@CurrentUser() user: AuthUser) {
    return user;
  }
}
```

Это пример защищённого маршрута `GET /v1/profile`. Маршруты без `@Auth()` остаются публичными; текущий health-маршрут также публичный. `@CurrentUser()` сам по себе не защищает маршрут и без guard может вернуть `undefined`.

В Swagger нажмите **Authorize** и вставьте JWT без префикса `Bearer`: Swagger добавит его к запросам защищённых маршрутов. Декоратор `@Auth()` также документирует ответ `401`. При ошибке авторизации API возвращает:

```json
{
  "success": false,
  "statusCode": 401,
  "message": "Пожалуйста, авторизуйтесь"
}
```

## Ошибки валидации

Обычные HTTP-ошибки возвращают `message` строкой. Если валидация находит одну или несколько ошибок, `message` содержит массив строк.

## Нормализация входных данных в DTO

В `src/common/transformers/` находятся вспомогательные функции для нормализации значений перед проверкой DTO:

- `normalizeString` удаляет пробелы в начале и конце строки. Пустой результат возвращается как `''`.
- `normalizeNumber` удаляет пробелы в начале и конце строки. Пустой результат возвращается как `''`, а непустая строка передаётся в `Number()`. Если преобразование невозможно, результатом будет `NaN`.

Обе функции сохраняют `null` и `undefined` без изменений, а значения неподходящего типа возвращают без преобразования. Используйте их явно с `@Transform()` только для тех полей DTO, где такая нормализация ожидаема.

### Пример использования `normalizeString`

```ts
import { Transform } from 'class-transformer';
import { IsDefined, IsNotEmpty, IsString } from 'class-validator';

import { normalizeString } from '@/common/transformers/normalize-string.transformer';

export class CreateUserDto {
  @Transform(normalizeString)
  @IsDefined()
  @IsString()
  @IsNotEmpty()
  name!: string;
}
```

Например, `"  Иван  "` преобразуется в `"Иван"`. Пустая строка и строка из пробелов после нормализации дают `''`, который отклоняет `@IsNotEmpty()`. `@IsDefined()` отклоняет `null` и `undefined`.

Валидатор `@IsOptional()` пропускает валидацию для `null` и `undefined`. Для `''` применяются остальные валидаторы поля.

### Пример использования `normalizeNumber`

```ts
import { Transform } from 'class-transformer';
import { IsDefined, IsInt, Max, Min } from 'class-validator';

import { normalizeNumber } from '@/common/transformers/normalize-number.transformer';

export class CreateUserDto {
  @Transform(normalizeNumber)
  @IsDefined()
  @IsInt()
  @Min(0)
  @Max(120)
  age!: number;
}
```

Например, `" 25 "` преобразуется в число `25` и проходит валидацию. `@IsInt()` отклоняет как `NaN`, полученный из `"abc"`, так и `''`, полученную из пустой строки или строки из пробелов.

Параметры `page` и `limit` в `PaginationDto` и `search` в `PaginationWithSearchDto` можно опустить. Если передать любой из них пустым или состоящим только из пробелов, запрос вернёт `400`.

Подбирайте валидаторы по требованиям поля:

- `@IsInt()` — для целых чисел, например номера страницы или количества элементов.
- `@IsNumber()` — для числовых значений, которые могут быть дробными.
- `@Min()` и `@Max()` — для ограничения диапазона.

### Правила использования

- Трансформеры изменяют входное значение, но **не заменяют валидацию**. Всегда добавляйте подходящие валидаторы.
- Не применяйте `normalizeString` ко всем строковым полям автоматически. Не используйте его для паролей, токенов и других значений, в которых пробелы могут иметь значение.
- Не дублируйте преобразование одного поля через `@Transform(normalizeNumber)` и `@Type(() => Number)` без необходимости.
- Для `PATCH`-запросов учитывайте разницу между `undefined` (поле не передано) и `null` (поле явно передано как пустое значение). Это может влиять на логику обновления.
- Обязательность поля задавайте валидаторами, например `@IsDefined()`, а тип и ограничения — `@IsString()`, `@IsNotEmpty()`, `@IsInt()`, `@IsNumber()`, `@Min()` и другими подходящими декораторами.

## Структура проекта

```text
prisma/
├── schema.prisma        # схема базы данных
└── migrations/          # миграции после их создания
src/
├── common/
│   ├── config/          # проверка окружения и настройки Swagger
│   ├── decorators/      # защита маршрутов и получение текущего пользователя
│   ├── dto/             # общие DTO пагинации и поиска
│   ├── filters/         # общий фильтр ошибок
│   ├── guards/          # проверка access-токенов
│   ├── interceptors/    # форматирование успешных ответов
│   ├── modules/         # глобальный JWT-модуль
│   ├── transformers/    # нормализация входных значений DTO
│   └── types/           # общие типы и интерфейсы
├── prisma/              # модуль и сервис доступа к базе данных
├── app.controller.ts    # корневой контроллер
├── app.module.ts        # корневой модуль
├── app.service.ts       # корневой сервис
└── main.ts              # запуск приложения и глобальные настройки HTTP
```

Новые предметные области удобно оформлять отдельными модулями внутри `src`. DTO и связанные с модулем сервисы размещайте рядом с его контроллером. Код, используемый несколькими модулями и не относящийся к конкретной предметной области, выносите в `src/common`.

## Проверки перед коммитом

При локальном `npm ci` скрипт `prepare` устанавливает Git-хуки Husky. Перед коммитом хук запускает `npm run precommit`. Для файлов, добавленных в индекс, `lint-staged` выполняет следующие команды.

- `eslint --fix` для `src/**/*.ts` исправляет форматирование через подключённый Prettier и другие ошибки, для которых ESLint поддерживает автоисправление, например порядок импортов.
- `prettier --write` форматирует `prisma.config.ts` и файлы с расширениями `.md`, `.mjs`, `.json`, `.yml` и `.yaml`.

Затем `format:check` проверяет форматирование рабочей копии, включая файлы вне индекса. Если любая команда завершается с ошибкой, коммит останавливается.

Для ручной проверки всего исходного кода без изменения файлов:

```bash
npm run lint
npm run format:check
npm run typecheck
```

GitHub Actions выполняет эти проверки и запускает `npm run build` при пуше в `main` и в pull request с целевой веткой `main`. На шаге `npm ci` переменная `HUSKY: '0'` отключает установку Git-хуков. Скрипт `postinstall` генерирует Prisma Client.

## Стиль кода

Для файлов и каталогов используйте `kebab-case`, для классов — `PascalCase`, для переменных и функций — `camelCase`. Форматирование определяет Prettier, а правила качества кода — ESLint; перед коммитом они применяются к подготовленным TypeScript-файлам автоматически.

### Импорты и alias

Alias `@/` указывает на каталог `src/` и настроен через `paths` в `tsconfig.json`.

- Для соседних файлов и связей внутри одного модуля используйте относительные пути: `./` или короткие `../`.
- Для обращений к другим модулям, общему коду и сгенерированному Prisma Client используйте `@/`.
- Импорты внешних пакетов и встроенных модулей Node.js оставляйте без alias. Сгенерированный код Prisma вручную не редактируйте.

```ts
// Соседний файл внутри src/prisma
import { PrismaService } from './prisma.service';

// Другие части проекта
import type { ServiceMessageResponse } from '@/common/types/service-response.types';
import { PrismaClient } from '@/generated/prisma/client';
```

При сборке через `npm run build` Nest CLI преобразует alias в относительные пути в JavaScript. Выбор между относительным путём и alias — соглашение проекта; ESLint проверяет сортировку импортов, но не обеспечивает соблюдение этого правила.

### Остальные соглашения

В Prisma называйте модели в `PascalCase`, а их поля — в `camelCase`. Названия таблиц в PostgreSQL задавайте в `snake_case` через `@@map`.

В IDE можно включить форматирование Prettier при сохранении. Комментарии добавляйте там, где они объясняют причину решения или неочевидное поведение; очевидный код не требует пересказа.
